# Sniffer mirror path validation

Does the bridge's `sniffer` command (eth0/T1S → eth1 → PC mirror, used to watch
T1S bus traffic with Wireshark) actually deliver **every** frame to the PC, or
can frames get lost along the way? This test answers that with real UDP and
TCP traffic and an automated completeness check, instead of eyeballing a
Wireshark window.

Generated by `sniffer_capture_test.py` (`python scripts/sniffer_capture_test.py`,
`--help` for all options). Source data: `sniffer_capture_results.log`.

## What the test does

1. Enables `sniffer` on the bridge - it stops forwarding and instead mirrors
   every frame it sees on eth0 (T1S) out to eth1, for the PC to capture.
2. Runs real `iperf` UDP and TCP traffic **directly between Follower A and
   Follower B** (both directions) - they talk to each other straight over the
   T1S bus; the bridge in sniffer mode is a passive tap, not a participant.
3. `tshark` on the PC records everything arriving on its NIC during each test.
4. Afterward, the capture is checked against the real, independently-verified
   ground truth of what was actually sent/received - not just "some packets
   showed up in Wireshark."

## How completeness is actually verified

- **UDP:** every iperf UDP datagram carries a 32-bit sequence id as the first
  4 bytes of its payload. The script extracts that id from every captured
  packet and checks that **no id is missing** between the lowest and highest
  one seen - a gap means a real frame never reached the PC. The expected
  count comes from the *sender's own* "packets attempted" counter (its own
  outgoing sequence counter - trustworthy, since it doesn't depend on
  feedback from the far end, unlike the sender's self-reported *loss*, which
  is meaningless for a pure UDP sender, see `FALLSTRICKE.md` 2026-08-27).
- **TCP:** compared by total bytes - the receiving Follower's own `iperf -s`
  session report (real received bytes) against the total TCP payload bytes
  actually present in the capture for that connection (95% tolerance for
  measurement/timing slop).
- **Frame-length sanity check (both):** a captured frame shorter than what
  its own IP/UDP header claims would mean real payload bytes are missing
  from the mirror - not just harmless trailing padding. None of the runs
  below triggered this.

## Results (2026-08-28, `--udp-rate 10`, `--duration 5`)

| Test | Requested | Result |
|---|---|---|
| UDP Follower A → Follower B | 10 Mbit/s | **COMPLETE** - 4013 data + 10 end-marker datagrams captured, 0 missing (source sent 4022, throughput 9.43 Mbit/s - the T1S link's own ceiling, not a limit of the test) |
| TCP Follower A → Follower B | (self-tuned) | **COMPLETE** - 3,652,920 bytes / 2507 segments captured vs. ~3,650,000 expected (100.1%) |
| UDP Follower B → Follower A | 10 Mbit/s | **COMPLETE** - 4013 data + 10 end-marker datagrams captured, 0 missing |
| TCP Follower B → Follower A | (self-tuned) | **COMPLETE** - 3,652,920 bytes / 2507 segments captured vs. ~3,649,375 expected (100.1%) |

**Bottom line: the sniffer mirror path did not lose a single frame** across
either UDP or TCP, in either direction, at the T1S link's real throughput
ceiling (~9.4 Mbit/s). This was reproduced across multiple separate runs on
2026-08-28, not a one-off.

The "10 end-of-stream marker(s)" per UDP test are iperf's own closing
datagrams (sent with the sequence id's sign flipped, repeated up to 10 times
if unacknowledged) - not lost or duplicate data packets, just the normal
termination handshake showing up in the capture too.

## The bridge's own mirror counters (`sniffer 0` output)

Each run also prints the bridge's internal mirror statistics, e.g.:

```
dbg: rx_hook=113004 passed_filter=113004 pool_empty=0 no_eth1=0 tx_submitted=113004
dbg: ack_ok=113004 ack_fail=0 last_ack_res=0 max_len_submitted=1514 max_len_ok=1514
dbg: truncated=78446 (frames cut to 1514 bytes before mirroring, see SNIFFER_4_ERGEBNISSE.md)
```

`rx_hook == tx_submitted == ack_ok` with `ack_fail=0` confirms the bridge
itself believes it mirrored everything it saw. The large `truncated` count
looks alarming but is harmless for these tests: it comes from `eth0`'s
LAN865x driver over-counting each frame's length by 18 bytes (Ethernet
header + FCS that should have been stripped before handing the frame to the
stack - the same root cause documented in `FALLSTRICKE.md` 2026-08-27 for the
bridge's forwarding path). The mirror code's 1514-byte safety cap then trims
those already-inflated 1512/1514-byte frames back down - removing bytes that
were never real payload to begin with. Confirmed directly: comparing each
captured frame's real length against what its own IP/UDP header claims it
needs showed **zero** cases of actual data loss in any of these runs.

## A pitfall hit while building this test (fixed, keep in mind for reruns)

`--udp-rate` takes **Mbit/s**, not bps. Passing an iperf-style raw bps number
(e.g. `--udp-rate 9000000`, thinking "9 Mbit/s" in bps notation) is
interpreted as 9,000,000 **Mbit/s** = 9 Tbit/s, which overflows the embedded
iperf client's 32-bit rate field - it silently wrapped to a small or even
*negative* "Target rate" internally. The tests still passed by coincidence
(the real T1S link capped the actual rate anyway, regardless of the garbage
target), but the logged numbers were nonsense. `sniffer_capture_test.py` now
rejects any `--udp-rate` outside `0 < rate <= 100` up front with a clear
error instead of silently sending a broken value.

## Reproducing this

```
python scripts/sniffer_capture_test.py --udp-rate 10 --duration 5
```

Requires Bridge (COM8), Follower A (COM10) and Follower B (COM23) connected
and not held open by another tool, and `iperf_matrix_test.py` in the same
directory (its node config and iperf-CLI helpers are reused). See
`scripts/sniffer_capture_test.py --help` for all options.
